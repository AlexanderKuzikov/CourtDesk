# Архитектурные решения

## 2026-07-17: Создание проекта

- **Контекст:** Нужен оркестратор между CourtSniffer (поиск) и CourtFlow (мониторинг), который хранит состояние, предлагает сценарии и обслуживает как пользователя, так и внешнюю CRM.
- **Решение:** Создать отдельный репозиторий CourtDesk.
- **Обоснование:** Независимое версионирование, разделение зон ответственности.
- **Статус:** Утверждено.

## 2026-07-17: Хранение состояния — JSON

- **Решение:** JSON-файлы, атомарная запись (tmp + rename).
- **Обоснование:** SQLite избыточен на старте. JSON проще, прозрачнее, не требует infra.
- **Альтернативы:** SQLite — лишняя зависимость без явной выгоды.
- **Статус:** Утверждено.

## 2026-07-17: Коммуникация с Sniffer/Flow — REST

- **Решение:** REST API.
- **Обоснование:** Sniffer и Flow уже имеют HTTP API. Очередь избыточна.
- **Статус:** Утверждено.

## 2026-07-17: Валидация URL — в CourtDesk (Intake)

- **Контекст:** CourtFlow пока синхронный парсер с intake из watch/. Валидация URL внутри CourtFlow избыточна — он должен только парсить то, что получил. Классификация URL — задача оркестратора.
- **Решение:** Создать модуль Intake в CourtDesk. Он классифицирует вход: карточка дела → CourtFlow, поисковой запрос → CourtSniffer, мусор → отказ.
- **Обоснование:** Intake — глубокий модуль с одним публичным интерфейсом (`classify`). Вся сложность (парсинг URL, детект типа суда, разбор номера дела) внутри. CourtFlow и CourtSniffer не меняются.
- **Альтернативы:** Валидация внутри CourtFlow — размазывание ответственности.
- **Статус:** Утверждено.
