# CourtDesk — DECISIONS

Архитектурные решения, зафиксированные с датой и обоснованием.

---

## 2026-07-21: Единый проект (не микросервисы)

**Контекст:** Изначально CourtSniffer (поиск) и CourtFlow (мониторинг) — отдельные репозитории. CourtDesk задумывался как оркестратор над ними по HTTP.

**Решение:** Собрать всё в один проект CourtDesk. Sniffer и Flow заморозить.

**Обоснование:** Микросервисы без необходимости — лишние накладные расходы. Одна кодовая база, один деплой, нет сети между модулями. При необходимости разнести — проще разрезать монолит, чем собрать три проекта.

---

## 2026-07-21: Один package.json, не workspaces

**Решение:** Монопроект с пакетами в `packages/`, но без npm workspaces.

**Обоснование:** Все пакеты в одном процессе, одна версия зависимостей, `npm install` один раз.

---

## 2026-07-21: JSON-хранилище (не SQL)

**Решение:** JSON-файлы с атомарной записью (tmp + rename).

**Обоснование:** Объём данных небольшой (< 10 000 дел). SQLite даёт транзакции, но tmp+rename достаточно. При росте — миграция на SQLite без смены интерфейса store/.

---

## 2026-07-21: REST API (не GraphQL)

**Решение:** REST + JSON.

**Обоснование:** 1С умеет REST. 15 эндпоинтов — не GraphQL-задача.

---

## 2026-07-21: API и Web UI — один Express-процесс

**Решение:** Один сервер, два слоя: `/api/*` и статика `/`.

**Обоснование:** Экономия портов, нет CORS при разработке. Если понадобится — UI выносится за reverse-proxy.

---

## 2026-07-21: Search ≠ Parse (разные адаптеры)

**Решение:** Два набора адаптеров: search/ (поиск, name_op=r) и parse/ (парсинг карточки, name_op=case).

**Обоснование:** Разные URL, разный HTML, разный парсинг. Объединение создаст сложный универсальный адаптер, который сложнее тестировать и поддерживать.

---

## 2026-07-21: Core — единый источник типов

**Решение:** Все типы (CourtType, SearchResult, CaseCard, WatchedCase) — в `packages/core/types.ts`. Никаких копий по пакетам.

**Обоснование:** В трёх проектах типы разошлись. Единый источник гарантирует консистентность.

---

## 2026-07-21: Intake — один `classify`

**Решение:** Intake — глубокий модуль с единственным публичным интерфейсом `classify(input)`.

**Обоснование:** Вся сложность разбора URL/текста внутри. Адаптеры поиска и парсинга не занимаются классификацией.

---

## 2026-07-21: Дата вступления — только из поиска

**Решение:** `legalForceDate` берётся из поиска по номеру дела (name_op=r), не из карточки (name_op=case).

**Обоснование:** На сайте суда в карточке дела этой даты нет. CourtSniffer уже умеет извлекать из поиска.

---

## 2026-07-21: Нет расчёта сроков

**Решение:** Не рассчитываем сроки апелляции/вступления. Только фиксируем факт: `legalForceDate` появилась / не появилась.

**Обоснование:** Слишком много нюансов (дата изготовления мотивировки, обжалование почтой). Юридических гарантий не даём. Максимум — цветовая индикация / напоминание «давно вынесено, но не вступило».

---

## 2026-07-21: userId — просто поле фильтрации

**Решение:** `userId` — опциональное строковое поле. CRM/UI сами фильтруют по нему.

**Обоснование:** Объём данных мизерный. Нет смысла городить ACL и разграничение доступа.

---

## 2026-07-21: Нет авторизации

**Решение:** API без аутентификации. Сервер слушает на внутреннем интерфейсе локальной сети.

**Обоснование:** Все пользователи в одной локальной сети. При необходимости добавить — layer внедряется middleware.

---

## 2026-07-21: CourtSniffer и CourtFlow — архив

**Решение:** Репозитории замораживаются. README содержит ссылку на CourtDesk.

**Обоснование:** Весь функционал мигрирует в CourtDesk. Двойная поддержка — лишняя работа.

---

## 2026-07-21: Парсинг по расписанию + ручной старт

**Решение:** Scheduler работает по расписанию (cron-like). Ручной запуск: `POST /api/parse/run` с `{ mode: "full" | "new" | "errors" }`.

**Обоснование:** Полный парсинг при каждом изменении избыточен. Достаточно периодической проверки.
